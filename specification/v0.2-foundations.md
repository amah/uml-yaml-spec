# UML YAML v0.2: foundations (draft normative)

This revision expands the v0.1 prototype. It is **not** a complete UML 2.5.1 serialization. UML metaclass names are aligned conceptually with UML 2.5.1; the YAML keys are project-specific serialization choices.

## Core semantics

- **Element:** stable `id`, documentation, ownership through containment.
- **NamedElement:** `name`, optional `visibility`; qualified names are derived from containment, not persisted as identities.
- **Namespace / Package:** recursive `packagedElements`; IDs are unique within the document, regardless of namespace.
- **Type / TypedElement:** `typeRef` points to a classifier or recognized primitive type.
- **Classifier:** `generalizations` is a sequence of references to parent classifiers. Cycles are invalid.
- **MultiplicityElement:** `multiplicity.lower` is nonnegative; `upper` is a nonnegative integer or `*`. The upper bound MUST NOT be smaller than the lower bound.
- **ValueSpecification:** the draft includes LiteralString, LiteralInteger, LiteralBoolean, and LiteralNull. This is not the full UML ValueSpecification hierarchy.
- **Constraint:** `ownedRules` includes `constrainedElements` and a typed `specification`. No expression execution semantics are implied.
- **DirectedRelationship:** Dependency and Realization have `clients` and `suppliers`.
- **Association:** `memberEnds` have stable IDs, referenced types, multiplicity, and aggregation. Complete UML end ownership, navigability, and redefinition semantics remain pending.

## Profiles

- `uml:Profile` may contain `uml:Stereotype` elements.
- `uml:Stereotype.extensions` identifies extended metaclasses.
- `tagDefinitions` declares typed tagged-value properties.
- `stereotypeApplications.values` uses typed ValueSpecifications; values MUST match the stereotype's tag definitions.
- The containing model or package MUST apply the defining profile.
- Stereotype inheritance and metaclass compatibility are semantic validation responsibilities.

## Identity and reference rules

IDs are nonempty, unique within a document, and stable across renames. Built-in references such as `uml:PrimitiveTypes::String` and `uml:Component` are reserved external symbols; a future specification will define a formal registry. Unresolved references are invalid unless a declared external reference mechanism permits them.

## What JSON Schema cannot establish

Schema validation does not prove reference resolution, UML inheritance validity, profile applicability, multiplicity ordering, metaclass-specific ownership, or complete UML semantics. Conformance requires a semantic validation implementation outside this specification repository.

## Migration from v0.1

- `apiVersion` changes to `uml-yaml.org/v0.2`.
- Multiplicity is grouped under `multiplicity: {lower, upper}`.
- Association ends and parameters now require stable IDs.
- Tagged values use typed `ValueSpecification` objects.
- Additional classifier and directed-relationship metaclasses are recognized.

These are breaking serialization changes. v0.1 remains available as a historical draft.
